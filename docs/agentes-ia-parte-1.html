Agentes de IA

Qué son, qué pueden hacer por nosotros y cómo empezar a usarlos sin romper nada.

Duración: 15–20 min Nivel: introductorio Enfoque: desarrollo de software

Definición

¿Qué es un agente?

1

Modelo (LLM)

Interpreta el objetivo y el contexto, razona y decide el siguiente paso.

2

Herramientas

Lee y escribe archivos, ejecuta comandos, corre tests, consulta APIs y la web.

3

Contexto

Mantiene el hilo de la tarea, recuerda decisiones y revisa los resultados.

No solo responde: actúa en un ciclo hasta cumplir el objetivo o quedarse sin camino.

Cómo funciona

El bucle del agente

Objetivo"Arregla el bug del login"
→
PlanLeer el código, reproducir, proponer un fix
→
AcciónLee archivos, corre tests, edita
→
ObservaciónFalla algo: ajusta el plan y repite
La diferencia clave: verifica su propio trabajo con herramientas, no solo "cree" que funcionó.

Capacidades

¿Qué puede hacer hoy?

Leer y editar código

Navega el repo, entiende patrones y aplica cambios coherentes.

Ejecutar comandos

Instala, compila, corre tests y lee la salida para corregir.

Buscar en el codebase

Encuentra dónde se usa algo sin que le digas el archivo exacto.

Consultar la web y APIs

Documentación, issues, ejemplos y respuestas de servicios externos.

Git y pull requests

Crea ramas, revisa diffs y prepara descripciones de PR.

Documentar

Genera READMEs, ADRs, comentarios y guías de onboarding.

Cómo delegar

Una tarea bien pedida

  • Contexto: repo, stack, rama, convenciones.
  • Objetivo: un resultado concreto y observable.
  • Restricciones: qué no tocar, qué no instalar.
  • Criterio de éxito: cómo sabremos que terminó.
Contexto: API Node + TypeScript, tests con vitest, rama feature/rate-limit. Objetivo: Añadir rate limit al endpoint POST /login. Restricciones: Sin dependencias nuevas. Sigue el patrón de los middlewares existentes. Éxito: Tests pasan y el diff es pequeño y revisable.
Un buen prompt se parece mucho a un buen ticket.

Realidad

Límites y riesgos

Lo que hace bien

  • Tareas acotadas y repetitivas.
  • Explorar código desconocido rápido.
  • Escribir la primera versión de tests.
  • Iterar cuando hay feedback claro.

Dónde falla

  • Inventa APIs o supuestos que no existen.
  • Pierde contexto en tareas muy grandes.
  • Puede romper cosas si tiene permisos de más.
  • Puede exponer secretos si se los pegas.
Regla de oro: confía, pero verifica.

Buenas prácticas

Cómo usarlos bien

  • Tareas pequeñas y con criterio de éxito claro.
  • Dar contexto: archivos, comandos, convenciones.
  • Tests como red de seguridad, siempre.
  • Permisos mínimos: solo lo que necesita.
  • Revisar el diff completo, no solo el resumen.
  • Nunca pegar credenciales ni datos sensibles.
Empieza en tareas de bajo riesgo y sube la autonomía gradualmente.

Ecosistema

Herramientas

En la terminal

Agentes que viven en el repo y usan tus comandos: opencode, Claude Code, Aider.

En el IDE

Integrados en el editor, con más o menos autonomía: Cursor, Copilot, Windsurf.

En la nube

Agentes que toman issues y abren PRs de forma asíncrona.

El panorama cambia rápido: elige por integración, permisos y trazabilidad, no por moda.

Siguiente paso

Cómo empezar mañana

1

Elige algo real

Un bug pequeño, un test faltante o un refactor acotado.

2

Pide el plan

Antes de ejecutar: que explique qué va a hacer y por qué.

3

Revisa y mide

Diff, tests y tiempo ahorrado. Ajusta la autonomía según el resultado.

Métrica simple: tiempo, calidad y retrabajo. Si el retrabajo sube, la tarea era demasiado grande.
